# Recommendation Engine

Full reference for the two rule sets the Resilience Agent runs against a discovered topology, and how each rule is evaluated.

The recommendation system has **two independent categories**:

1. **Resiliency recommendations** — analyze the topology *structure* and suggest **new infrastructure** to add. In the **Recommended** view these render as **green dashed ghost nodes and edges** overlaid on the existing diagram. Resiliency rules run **per DX Gateway** — each DXGW is assessed independently against its own target tier, so accounts with multiple DXGWs get one set of ghost overlays per gateway.
2. **Best practice checks** — operational and configuration findings surfaced with a severity, shown in the Resilience Status checklist and (for faults) as colored edges in Live Status mode.

## 1. Resiliency rules

**12 `ruleId`s from 9 rule functions** — 6 functions in `resiliency-rules.ts`, 3 in `public-vif-rules.ts`. Every recommendation here is severity **Info** except `no-tgw` and `single-vgw`, which are **Warning**: a tier gap may be a deliberate product decision (a dev environment intentionally sitting on one connection), so it is never graded Critical. Observed faults are the best-practice rules' job.

| Rule ID | Trigger | Recommendation | Signal |
|---|---|---|---|
| `single-dx-location` | Only 1 DX location serves this DX Gateway | Add a second DX location (ghost labels include the DXGW name when multiple gateways exist; reuses an existing location elsewhere in the topology when there is one) | `DescribeLocations` + `DescribeConnections` grouping |
| `vgw-single-dx-location` | Same check, for a **VGW reached over Direct Connect** | Same — ghost devices fan into `vgw-<id>` instead of `dxgw-<id>` | Same. Emitted by `ruleSingleDxLocation` with `gatewayKind='vgw'` |
| `single-connection-per-location` | A DX location serving this DXGW has only 1 AWS logical device (**Maximum target only** — a no-op at High) | Add a connection on a separate AWS logical device | `awsLogicalDeviceId` from `DescribeConnections` |
| `vgw-single-connection-per-location` | Same check, for a DX-reached VGW | Same | Same. Emitted by `ruleSingleConnectionPerLocation` with `gatewayKind='vgw'` |
| `no-tgw` | No TGWs exist but VGWs do | Consider migrating to Transit Gateway (**Warning**) | `DescribeTransitGateways` |
| `single-vgw` | Exactly 1 VGW and no TGWs | Add a redundant VPN Gateway (**Warning**) | `DescribeVpnGateways` |
| `lag-single-location` | LAGs exist at only 1 DX location | Add a LAG at a second location — a LAG is bandwidth aggregation, not site redundancy | `DescribeLags` grouped by location |
| `lag-redundancy-per-location` | A LAG location has no second device/LAG to fail over to | Add a redundant device or LAG at that location | `DescribeLags` + `awsLogicalDeviceId` |
| `pubvif-single-dx-location` | Public VIFs terminate at only 1 DX location | Add a second DX location for public VIF connectivity | `DescribeVirtualInterfaces` (public VIFs) + `DescribeConnections` grouping — only runs when public VIFs exist |
| `pubvif-single-connection-per-location` | A public-VIF DX location has connections on only 1 device (Maximum target only) | Add a redundant connection on a separate device | `awsLogicalDeviceId` from `DescribeConnections` — only runs when public VIFs exist |
| `pubvif-carried-max-gap` | A public VIF rides the same connection as a DX Gateway whose target tier is higher, so the shared carrier is upgraded past the public VIF's own tier | Surfaces the gap so the public endpoint path is assessed at the tier its carrier is actually being taken to | Carrier correlation between public VIFs and DXGW-scoped connections |

The three `pubvif-*` rules run through a dedicated public-VIF assessment path and only apply when the topology has public virtual interfaces; their ghost overlays attach to the **public-endpoints** node rather than a DX Gateway.

The `vgw-*` ids are not separate rules — a VGW reached over a private VIF has the same site/device redundancy posture as a DX Gateway, so the same two functions are re-run with `gatewayKind='vgw'` and only the ghost sink node id changes.

> **Where these rules' text appears:** on the canvas these rules manifest **only** as green ghost infrastructure. Their `title`/`description` strings are not rendered in the app UI — they reach the user through the HTML report's "How to improve resiliency" section and the chat system prompt.

## 2. Best practice rules

**33 rule functions → 38 `ruleId`s.** 33 are topology-wide (evaluated in `getAllBestPracticeResults`); the 2 SLA-precondition attestations run per DX Gateway and per VGW instead. The id count exceeds the function count because five rules emit a separate id on the healthy path — `bgp-route-limit-ok`, `dxgw-propagation-ok`, `bgp-session-stability-ok`, `dx-failover-testing-ok`, `logical-redundancy-ok` — so a "met" row is distinguishable from a finding.

Every rule is listed below. Two things about where they surface:

- **Six rules have no row in the on-screen Best Practices panel**: `blackhole-routes`, `vpc-no-hybrid-route`, `dxgw-propagation`, `bgp-session-stability`, `vpn-static-routes-only`, `vif-rate-limit-oversubscription`. `ResiliencyScoreCard.tsx` builds its checklist from 20 hand-written JSX blocks keyed on rule id, so these reach the user only through the **downloadable HTML report** and the **chat context**. Marked ⚠ in the tables. Newer rules instead go through the panel's `PASS_THROUGH_RULES` list, which forwards the rule's own `title`/`description` verbatim — one array entry rather than a hand-written block, which is why none of them is panel-less.
- The **pillar** (Architecture / Configuration / Operations) is a presentation grouping, not a field on the rules — the engine's only `category` is `'resiliency' | 'bestpractice'`. The panel assigns it in `ResiliencyScoreCard.tsx`; the HTML report keeps a parallel `RULE_CATEGORY` map in `useExportReport.ts`. That map currently omits the six panel-less rules plus `lag-min-links` and `vif-route-symmetry`, so **in the report those default to Configuration** regardless of the pillar this document lists them under.

Unlike the resiliency rules above (which are all evaluated against observed AWS data), best-practice checks vary in whether they can be verified automatically. The key question is **where the data lives**: AWS's APIs only expose AWS's side of the connection, so a rule can be checked automatically only if the thing it verifies is visible through an AWS API or CloudWatch metric. Many best practices are not — they depend on state that lives on **your own equipment or processes**: the on-premise router / customer gateway (BFD, BGP hold timers, advertised prefixes, Dead Peer Detection), your AWS Support plan, or your team's runbooks. AWS has no API for those, so the agent can't detect them; it can only remind you to check.

The **Detection** column in the tables below tells you which kind each rule is:

| Value | What it means | Does it depend on your account state? | Example |
|---|---|---|---|
| **API-supported** | The rule reads live state from an AWS API (SDK) or a CloudWatch metric and flags an issue based on what it finds. | Yes — it only flags a real, observed problem. | `vif-down` is flagged only when a VIF's BGP session is actually down, read from `DescribeVirtualInterfaces`. |
| **Partial** | The rule detects the AWS-side half of the setting via API, but the customer-premise half is not exposed, so a clean result is an attestation you should still verify. | Partly — the AWS side is observed; the on-prem side is not. | `vpn-dpd` reads the AWS tunnel's DPD action, but can't see the Dead Peer Detection config on your customer gateway. |
| **Guidance** | The rule always appears when it's relevant to your topology shape. AWS doesn't expose the underlying state, so it's an informational reminder or attestation, not a detected fault. | No — it is always shown, regardless of the actual setting. | `bfd-guidance` always recommends enabling BFD, because BFD runs on your router and AWS has no visibility into it. |

### 2.1 Architecture

Rules related to topology design, redundancy strategy, and structural decisions.

| Rule ID | Detection | Check | Signal / Notes |
|---|---|---|---|
| `no-vpn-backup` | API-supported | DX without a Site-to-Site VPN backup path | Topology correlation between DX + `DescribeVpnConnections` |
| `cgw-redundancy` | API-supported | All VPN connections terminate on a single Customer Gateway — deploy 2+ CGWs to avoid a device-level SPOF | `DescribeCustomerGateways` + VPN assignment |
| `dx-partner-diversity` | API-supported | All DX connections come from the same partner / last-mile provider — names the actual alternative partners available at the locations you already use | `DescribeConnections` — `partnerName` + `DescribeLocations` `availablePartners` |
| `shared-logical-device` | API-supported | One AWS logical device carries VIFs for **two or more routing domains** — every other device check is scoped inside a single DX gateway, so each gateway can pass on its own while they all sit on the same hardware | `awsLogicalDeviceId` on `DescribeVirtualInterfaces`, grouped by device across the whole estate. **Critical** when a shared device is some domain's *only* path (losing it takes that gateway to zero), otherwise **Warning**. Silent when AWS reported no device identity |
| `logical-redundancy` | API-supported | AWS's own verdict on the interconnect terminating the port. `hasLogicalRedundancy = "no"` is evidence no device count can produce — it describes partner-side hardware the topology cannot see | `DescribeConnections.hasLogicalRedundancy`. **Warning**, grouped by location; emits `logical-redundancy-ok` (Info) when every graded connection reports redundancy. Skips inferred (hosted-VIF) connections and is silent when AWS reported nothing |
| `unused-dxgw` | API-supported | A DX gateway with no VIFs and no gateway associations carries no traffic, counts against the per-account gateway quota, and makes the topology unreadable — a decommissioned gateway looks identical to a half-built one | `DescribeDirectConnectGateways` + VIF / association cross-reference. **Info** |
| `dxgw-propagation` ⚠ | API-supported | No Direct Connect gateway attachment propagates into a TGW route table (or propagation is not yet `enabled`) — the table can look healthy while carrying no path on-premises | `GetTransitGatewayRouteTablePropagations` (a `Get*` action, **not** covered by `ec2:Describe*`) via the opt-in `includePropagations` fetch. **Warning.** Tables whose `propagations` is `undefined` (not fetched / denied) are **skipped entirely** — a missing permission never reports as a blackhole. Emits `dxgw-propagation-ok` (Info) when every checked table propagates |
| `enterprise-support-required` | Guidance | SLA precondition: Enterprise Support for the 99.9% / 99.99% tiers | Cannot query the Support plan from these APIs — attestation-only when target tier is High/Maximum |
| `well-architected-review-required` | Guidance | SLA precondition: a Well-Architected Review for the 99.99% tier | Cannot query WA Review state — attestation-only |
| `dx-location-redundancy` | Guidance | Metro vs geographic DX location diversity trade-off | Risk-profile recommendation — always informational |
| `sla-awareness` | Guidance | Reminder of the three published DX SLA tiers (95% / 99.9% / 99.99%) and what each requires | Informational prompt based on current shape |
| `resiliency-toolkit` | Guidance | Pointer to the AWS DX Resiliency Toolkit for production workloads | Informational |

### 2.2 Configuration

Rules related to BGP/BFD settings, connection state, and protocol tuning.

| Rule ID | Detection | Check | Signal / Notes |
|---|---|---|---|
| `vif-down` | API-supported | VIF BGP session not established | `DescribeVirtualInterfaces` — `virtualInterfaceState` + `bgpPeers[].bgpStatus`; shown as a red edge in Live Status mode |
| `connection-not-available` | API-supported | DX connection in a non-`available` state | `DescribeConnections` — `connectionState`; shown as a red edge in Live Status mode |
| `vpn-tunnel-redundancy` | API-supported | Both tunnels UP per Site-to-Site VPN — flag any VPN with fewer than both up | `DescribeVpnConnections` — `vgwTelemetry[].status` |
| `vpn-static-routes-only` ⚠ | API-supported | A Site-to-Site VPN configured with static routes only has no BGP session, so it cannot withdraw or re-advertise prefixes on failure — it is not a working DX backup despite being present | `DescribeVpnConnections` — `staticRoutesOnly`. **Warning.** Silent when no VPN reports the flag (older snapshots, mocks) |
| `lag-min-links` | Guidance | Configure LAG `min-links` — a LAG is bandwidth aggregation, not resiliency (all members land on the same AWS device at the same location). Without min-links a severely degraded LAG keeps forwarding at reduced capacity instead of failing over | Fires whenever any LAG exists (`DescribeLags`). **Info** — the `minimumLinks` value is not exposed on the LAG object, so this is a reminder, not a detection |
| `blackhole-routes` ⚠ | API-supported | A route matches traffic and then drops it — the path looks configured, nothing gets through, and it raises no error anywhere. Names the offending tables and up to 3 sample prefixes each | `SearchTransitGatewayRoutes` + `DescribeRouteTables` — `state === 'blackhole'`, across **both** TGW and VPC route tables. **Warning** |
| `vpc-no-hybrid-route` ⚠ | API-supported | An in-use VPC route table has no route pointing at a TGW, VGW or Cloud WAN core network — those subnets cannot reach on-premises however healthy the DX path is | `DescribeRouteTables`. Only considers tables that actually carry traffic (`main`, or with subnet associations); `igw-*` is **not** a hybrid target. **Info** — deliberately isolated subnets are legitimate, so it asks for confirmation |
| `bgp-route-limit` | API-supported | Accepted prefixes against the quota **actually enforced on that VIF**: its own inbound prefix-pool allocation where AWS reports one, otherwise the documented per-family default (100 each for IPv4 and IPv6; public VIFs 1,000, which pools do not apply to) | Denominator from `prefixQuotaFor()` — `DescribeVirtualInterfaces` `prefixPool.allocatedIpv4/Ipv6`, which is set per VIF and adjustable, so redundant siblings legitimately differ. Numerator from `acceptedByFamily()`: exact accepted routes from `ListVirtualInterfaceRoutes` (deduped by prefix — the same route installed on two logical devices is returned twice, which once produced "2200 of 1000") beat CloudWatch `AWS/DX` `VirtualInterfaceBgpPrefixesAccepted`, whose `IpAddressFamily` dimension gives the per-family split; a pooled-only metric or a route with no `addressFamily` counts as IPv4 so old snapshots still score. **Critical** at or over the ceiling, whatever the current BGP state — AWS drops the excess and documents that advertising past the allocated count drives the session into an idle state, so the report says the session *could go down* rather than asserting it is. **Warning** from 80%, **Info** below it or when neither source has data. The description points at the console's *In use* counter (which AWS enforces against and no released `@aws-sdk/client-direct-connect` models) so the reader can reconcile the two measurements; an earlier version carved out "above a reported allocation while the session is UP" as a separate two-counts-disagree warning, which asked the reader to reason about measurement provenance before acting on a number at its ceiling either way. Emits `bgp-route-limit-ok` on the healthy path. Dividing by a fixed 100 read a VIF at 18 of its own 20 as 18% and said nothing |
| `prefix-allocation-skew` | API-supported | Redundant VIFs on one routing domain have **unequal** allocations, so the domain can only absorb as many prefixes as its *smallest* one — every VIF can sit comfortably inside its own ceiling while failover onto the weakest path tears that session down | `prefixPool.allocatedIpv4` per VIF vs the domain's peak accepted count. **Warning** when the weakest path has under 20% headroom against that peak (a negative headroom is reported as "*N* short of that peak", not "-N spare"). Silent for single-VIF domains, for equal allocations, and when *any* sibling's allocation is unreported — partial coverage is unknown coverage, since the missing one could be the real minimum |
| `prefix-pool-exhausted` | API-supported | A connection's inbound prefix pool has nothing left to hand out: a new VIF on the port cannot be given an allocation, and an existing VIF's cannot be raised, without taking capacity back from another | `DescribeConnections` `prefixPool.unallocatedIpv4/Ipv6 === 0`. **Warning**, naming the family. `undefined` is **unknown, never zero** — AWS documents these counts as N/A for hosted connections and interconnects, so an all-hosted account must not be told its pools are exhausted; inferred connections are skipped for the same reason |
| `prefix-churn` | API-supported (CloudWatch) | The accepted-prefix count *moved* across the sampled window — routes are being withdrawn and re-advertised (a flapping session, an in-progress router change, intermittent summarization), and until it settles any headroom figure is measuring a moving target | `AWS/DX` `VirtualInterfaceBgpPrefixesAccepted` folded over the **whole** window with `Stat: 'Maximum'` → peak, floor and datapoint count. **Warning** when the spread is ≥2 prefixes *and* ≥20% of the peak. Requires `samples > 1`: one datapoint has no spread, and treating a missing floor as 0 would report every VIF as maximally unstable. Free — the same login-time metric the quota check already reads |
| `jumbo-frames` | API-supported | The path supports jumbo frames but the VIF is still at MTU 1500 — free per-packet overhead reduction on bulk transfers | `DescribeVirtualInterfaces` `jumboFrameCapable` vs `mtu`. **Info**, not a fault: the MTU must match end to end (VIF, customer router, instances) or traffic silently fragments or blackholes, and changing it resets the BGP session, so it is change-window planning rather than a fix |
| `bgp-auth-consistency` | API-supported | Some BGP sessions authenticate with an MD5 key and some do not. The **gap** is the finding — the protected sessions show what the intended standard is, so the unprotected ones are most likely an oversight | Presence only, from `bgpPeers[].hasAuthKey`. `DescribeVirtualInterfaces` returns the live secret (and `customerRouterConfig` embeds it again in plaintext), so the store keeps a **boolean and never the key**. **Warning**. Silent when the estate is uniform either way — all-or-none is a decision, not a gap — and when presence was never reported |
| `vif-rate-limit-oversubscription` ⚠ | API-supported | Per-VIF rate limits on one connection sum above the port bandwidth | `DescribeVirtualInterfaces.rateLimit` vs `DescribeConnections.bandwidth`. **Info** — over-subscription is a valid statistical-multiplexing design, so it prompts confirmation rather than asserting a fault. Only evaluated when every VIF on the port is rate-limited (an uncapped VIF can already use the whole port), and silent when no VIF carries a limit |
| `vpn-dpd` | Partial | Dead Peer Detection action configured on VPN tunnels | AWS-side DPD action (`DpdTimeoutAction` from `DescribeVpnConnections` → `TunnelOptions`) is detected — **Warning** when any tunnel is set to `none` (switch to clear/restart); otherwise **Info**, an attestation that the customer-gateway-side DPD config (not exposed via API) is in place |
| `bfd-guidance` | Guidance | Enable BFD on the customer router for sub-second failover detection | BFD runs on the CPE; no AWS-side visibility |
| `bgp-timers-fallback` | Guidance | If BFD isn't supported, tune the BGP hold timer down from the 90s default | BGP timers live on the CPE |
| `consistent-prefix-advertisement` | API-supported (BGP routes) / Guidance | Redundant VIFs in a routing domain accept the same prefix set — asymmetry blackholes traffic on failover | Once routes are fetched, compares accepted prefix sets per DXGW/VGW from `ListVirtualInterfaceRoutes` and reports the actual difference (**Warning** on mismatch, **Info** "verified matching" when all pairs align). Falls back to guidance when route data is absent (routes not fetched, permission denied, or v1 snapshot). The **Route diff** panel on a DXGW node (VISUALIZATION.md §6.6) is the prefix-by-prefix drill-down of this finding |
| `vif-route-symmetry` | API-supported (BGP routes) / Guidance | Summarize prefixes; keep VIF routing symmetric | With route data, flags prefixes already covered by a less-specific prefix on the same VIF — each wastes one of the per-family accepted-prefix slots (**Warning**). Falls back to guidance otherwise |

### 2.3 Operations

Rules related to monitoring, testing, and runbook maintenance.

| Rule ID | Detection | Check | Signal / Notes |
|---|---|---|---|
| `dx-failover-testing` | API-supported (test history) / Guidance | Has redundancy actually been *exercised*, not just configured? | `ListVirtualInterfaceTestHistory` per VIF (a `List*` action, **not** covered by `directconnect:Describe*`), fetched on demand. Grades on four outcomes: a **failed** test is **Critical**; queried-with-none-on-record is worded "no failover test found in available history" (never "never tested" — only tests started through the AWS API are recorded); a stale pass is a reminder; all-recent-and-passing emits `dx-failover-testing-ok`. Falls back to the original unconditional guidance when the map is absent. The mutating siblings `StartBgpFailoverTest` / `StopBgpFailoverTest` force a production BGP peer down and are deliberately **absent from the codebase and the chat tool surface** |
| `bgp-session-stability` ⚠ | API-supported (CloudWatch) | A session that is "up" right now can still have dropped repeatedly — `DescribeVirtualInterfaces` cannot tell the two apart | CloudWatch `AWS/DX` `VirtualInterfaceBgpStatus` with `Stat: 'Minimum'` (`Average` rounds a 90-second drop away), using only streams whose `IpAddressFamily` matches the VIF's configured `addressFamily` because AWS can publish an all-zero stream for the unconfigured family. Counts up→down **edges** so one long outage is one flap. **Warning** at 3+ drops on any VIF, else **Info**; emits `bgp-session-stability-ok` when the sampled window is clean. On demand only (billed per metric retrieved) and **silent when never fetched** — it never implies stability it did not measure. Retention bounds the claim: 5-minute data 63 days, 1-hour 455 days, so windows over 7 days drop to `Period: 3600` and can hide a flap that healed inside the hour |
| `recent-aws-issue` | API-supported | AWS Health has an `issue` event — a fault AWS has already **confirmed** on this account — in the lookback window. Distinct from the maintenance calendar and from the executive summary's first driver, both of which handle only `scheduledChange`; before this rule an AWS-confirmed outage reached the user solely as a coloured dot on the calendar | `DescribeEvents` with `eventTypeCategory: 'issue'` (90-day `startTimes` floor — issues are past-dated and unbounded). **Warning** while any event is open, or on repeats (more than one is a pattern, and the strongest available argument for a second location or provider), else **Info**. Names affected resources only when AWS itemised ones this account owns; an `ACCOUNT_SPECIFIC` event with none says so rather than inventing a scope. `PUBLIC` events are broadcast region-wide regardless of footprint and are excluded |
| `failover-runbooks` | Guidance | Maintain documented DX/VPN failover runbooks with escalation paths | Process recommendation |

## 3. How each rule is sourced

Every rule encodes an AWS-documented best practice from:

1. **[AWS Direct Connect Resiliency Toolkit](https://docs.aws.amazon.com/directconnect/latest/UserGuide/resilency_toolkit.html)**
2. **[AWS Well-Architected Framework — Reliability Pillar](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/welcome.html)**
3. **[AWS Direct Connect Best Practices](https://docs.aws.amazon.com/directconnect/latest/UserGuide/best-practices.html)**
